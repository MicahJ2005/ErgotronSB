Version 1.0 · Documentation release: October 6, 2026

Marketing_Submission__c provides a durable record of each marketing form submission, separate from the Lead or Contact and from the work generated for Sales. Use an autolaunched Flow to capture the submission, then a record-triggered Flow to process it. This gives new marketing use cases a reusable intake contract without requiring an Apex class for every action.

Verification scope: All 18 fields below were verified in the Ergotron FULL sandbox on October 6, 2026. Flow behavior and operational readiness reflect the October 1 sandbox handoff; they were not re-tested for this documentation. Recommendations are explicitly marked as proposed.

Architecture and record ownership

The object represents one submission event, not one person or one form. Three submissions by the same person should produce three records. A retransmission of the same event should preserve the original record.

The capture Flow owns the submitted facts. The processor owns relationships, status, and outcomes. The Task owns the Sales work. Do not replace the original answers when a Task is completed or a person submits another form. Current preservation comes from capture's insert-or-skip behavior; it is not a globally enforced immutable-record policy.

Field dictionary — submission identity and source facts

These eight fields correspond to the eight Text inputs of Marketing_Submission_Capture. Field types below are the Salesforce storage types, which can differ from the Flow input type.

Field and API nameType / inputPurpose and design guidance
Submission Key — Submission_Key__cText(255), unique case-insensitive, External ID; submissionKeyIdentity of one source event. Reuse the same value for retries; use a different value for each genuine submission. Proposed convention: source + business unit + source event ID. Do not use email, prospect ID, or form key alone. Case-only differences are duplicates. Indexed.
Form Key — Form_Key__cText(255); formKeyStable form identifier for routing and reporting. Use this to select configured behavior; keep it stable when the display name changes. Proposed: qualify by business unit if form IDs can overlap. Currently not indexed.
Form Name — Form_Name__cText(255); formNameHuman-readable name at submission time. Useful in Task descriptions and Sales history. Keep as a snapshot; avoid using a changeable name as the routing key.
Prospect ID — Prospect_ID__cText(80); prospectIdSource Account Engagement prospect identifier for support and reconciliation. It is not a Salesforce record ID or relationship. Proposed: pair with business unit identity before cross-unit matching.
CRM Record ID — CRM_Record_ID__cText(18); crmRecordIdSource-supplied Salesforce Lead or Contact ID. Processor currently exact-matches this value. Text storage does not enforce referential integrity or validate object type. A populated ID does not prove the person predated the submission.
Submitted Email — Submitted_Email__cText(254); submittedEmailEmail as submitted, retained even if the person's current email changes. This is Text, not Salesforce Email type, so explicit validation is needed. Do not treat email alone as a unique person identifier.
Submitted At — Submitted_At__cDate/Time; submittedAtUtcTime the source event happened. Input convention is UTC YYYY-MM-DD HH:MM:SS. Supports chronology and intake-delay analysis. Blank input remains null; invalid date text currently faults capture. Do not substitute Salesforce intake time and call it source time.
Submission Details — Submission_Details__cLong Text Area(32768); submissionDetailsPreserved answers and context for Sales or later processing. A readable snapshot can include question labels and answers. JSON is a possible agreed format, but this field does not automatically parse JSON or make arbitrary keys reportable. Promote fields needed for filtering or routing into typed fields.

Current replay behavior: capture trims a supplied key and skips an existing record with that key without overwriting answers. If no key is supplied, it uses the Flow interview GUID. That fallback identifies an invocation, not a source event, and cannot recognize retries. Concurrent inserts can still cause a duplicate-key fault even though the unique constraint prevents duplicate records.

Source fidelity matters: a merge field populated from the latest prospect profile is not necessarily a snapshot of the particular form submission. Verify how each form supplies its event ID, timestamp, and answers, including two rapid consecutive submissions.

Field dictionary — relationships and processing

These five custom fields are processing outputs. Do not expose them as marketer-controlled External Action inputs.

Field and API nameTypePurpose and design guidance
Lead — Lead__cLookup(Lead), indexedResolved Lead relationship. Enables related lists and person-level reporting. Retain it after conversion to preserve provenance; it may coexist with Contact.
Contact — Contact__cLookup(Contact), indexedResolved Contact relationship, populated directly or after Lead conversion. Current conversion Flow fills an empty Contact link while retaining Lead. A relationship does not itself grant users access to the person record.
Processing Status — Processing_Status__cText(80)Operational lifecycle: currently Received, Pending CRM Match, Routed, or Failed. It is not a picklist, so consistent spelling is essential. Proposed: controlled values and guarded transitions, with a separate review state when ambiguity handling is implemented.
Processing_Message — Processing_Message__cText(255)Short operator explanation of a pending/failed outcome. Actual label contains an underscore. Proposed: concise reason codes and actionable text; store longer execution diagnostics separately. Avoid putting secrets or unnecessary personal data here.
Follow Up Task ID — Follow_Up_Task_ID__cText(18)ID of the created Task and a guard against normal reprocessing. It is not a lookup, does not enforce that the Task still exists, and is not a concurrency lock. Do not clear it to force another run. For multiple actions per submission, use proposed child execution records instead of adding an ID field for each action.

Preserve the distinction between the raw source CRM ID and the resolved lookups. The current retry procedure permits correcting CRM Record ID. If audit requirements demand an untouched original identifier, add a separate reconciliation input and preserve the original source value.

These five standard fields complete the 18 fields shown in Fields & Relationships.

Useful system fields beyond this visible field list include Id for record links and relationships, CreatedDate for Salesforce intake time, and LastModifiedDate for the latest update. LastModifiedDate is not a substitute for an explicit processing-completion timestamp.

The October 1 handoff recorded reports, search, and history enabled; individual tracked fields and broader access were unfinished. Object-level history enablement alone does not mean every field is tracked. Activities were disabled, so current Tasks relate to the person through WhoId rather than using this object as WhatId.

Exposing the capture Flow through a Marketing App Extension

Salesforce supports Flow Builder invocable actions for External Actions. Register the active autolaunched Marketing_Submission_Capture Flow as the extension's Action Type; the object itself is not the callable action. Grant the B2BMA integration user appropriate Flow access. Use the generated schema, retain its required fields and Parameters, and keep Properties, View, and Required sections. The schema supports string and number inputs; these eight inputs are strings. Activate both the action and extension. Salesforce External Actions guide.

Configure the form or form handler's Execute External Action completion action to call this intake action. External Action completion actions support both forms and form handlers. Salesforce completion-action guidance.

Proposed contract rules, not current validation:

  • Require a stable formKey, submissionKey, and valid submittedAtUtc.
  • Supply formName and submissionDetails sufficient to explain the request to Sales.
  • Supply available person identifiers, allowing delayed CRM linkage to enter reconciliation rather than silently dropping the event.
  • Validate field lengths, timestamp format, and allowed source/form identifiers before downstream actions.
  • Use tested source mappings. Do not invent HML tokens or assume every event-specific value is available as a merge field.

Expose the smallest useful set of marketer-editable inputs. Use form configuration for stable values and verified source mappings for event values. Keep ownership, status, Task IDs, and arbitrary executable Flow names out of the public input contract.

Current processing lifecycle

The October 1 active baseline was:

ComponentRecorded behavior
Marketing_Submission_CaptureAutolaunched intake; insert with Received status or skip an existing submission key.
Marketing_Submission_ProcessAfter-save asynchronous processing when a record newly meets Received status with a blank Task ID.
Marketing_Submission_Link_Converted_LeadOn qualifying Lead conversion, populate empty Contact links on related submissions; preserve Lead links.
StatusMeaningOperational response
ReceivedIntake committed and eligible for processing.Monitor age. A long-lived record can indicate a processing fault that was not caught.
Pending CRM MatchSupplied CRM ID did not resolve to a Lead or Contact.Reconcile identity and retry explicitly. Do not assume a new person or create a duplicate Lead.
RoutedThe processor created a Task and stored its ID.Sales follows up. This does not mean the Task is completed or every future workflow succeeded.
FailedA handled failure, such as missing queue or failed Task creation.Resolve cause, inspect any existing outcomes, and retry under controlled conditions.

The current processor resolves exact CRM IDs, links the person, and creates an Open, Normal-priority Task owned by Re_Engagement_Task_Queue. It prefers the Contact when available, including a converted Lead's Contact. Task subject is “Marketing form submission - follow up”; Description contains Submission Details. Richer context and revised subject were draft work.

Material limitation: current V1 does not distinguish a connector-created new Lead from someone who existed before the form submission. An existing CRM ID at processing time is insufficient evidence. No automatic email matching, new-Lead creation, or scheduled reconciliation is implemented in these Flows.

For a pending/failed record with no Task ID, the documented manual retry corrects identity as needed and changes status back to Received. Merely editing a record already meeting the entry condition does not necessarily retrigger it. Concurrent retries and Task-level uniqueness need stronger controls before high-volume operation.

Extending the design without one Apex class per use case

Keep capture stable and add behavior behind the saved submission. Proposed examples include Campaign Member updates, Case creation, Sales Tasks, or supported declarative integration actions. These are extension patterns, not current implemented outcomes.

Change neededRecommended extension
Another form uses an existing processAdd configuration keyed by stable Form Key and source/business unit. Reuse the capture contract and processing pattern.
Different queue, priority, campaign, or follow-up SLAStore approved routing settings in Custom Metadata and have the processor resolve them. Use stable developer names or portable configuration rather than embedding sandbox record IDs.
A genuinely new business processAdd an explicitly selected subflow or Flow branch with a defined input/output contract. Test it separately and invoke it from the dispatcher.
New answers needed for decisions or reportingAdd typed fields and explicit mappings; retain the full original snapshot in Submission Details.
Multiple independent actions per submissionAdd a child execution object, one record per intended action, with its own status and target reference.

A Custom Metadata row does not automatically make Flow invoke any arbitrary Flow API name. Use supported, explicitly configured branches/subflows. “No Apex per use case” is feasible for work supported by Flow and available actions; it is not a promise that all parsing, concurrency, or integration requirements can be handled without code.

Proposed additions — none of these fields or objects are in the verified inventory:

  • Submission source, business unit, and schema version for multi-source contracts and migrations.
  • Processing completion time, attempt count, next retry time, and a structured reason code for operations.
  • A child Marketing Submission Action object with parent submission, action key, status, attempts, next retry, and target record ID.
  • A unique action execution key derived from submission identity plus a stable action identifier. This separates event replay protection from individual outcome replay protection.

For example, one submission could create a Task and add a Campaign Member. Each action should record its own success, so retrying a failed campaign update does not recreate the successful Task. Make new behavior opt-in through approved configuration; old submissions should not acquire new side effects merely because configuration changed.

Scaling and operational controls

This is a scalable foundation because ingestion is small, source records survive downstream failures, and processing can evolve independently. It is not an unlimited-throughput or exactly-once guarantee. Establish expected peak volume, latency, and retention, then test against this org's actual automation and limits.

Capture and consistency. Enforce input validity and a real source event key. Preserve submitted facts, restrict edits to snapshot fields, and handle duplicate-key races explicitly. Avoid overwriting existing submissions through External ID upserts. A unique submission key alone does not guarantee unique Tasks.

Identity and timing. Do not depend on connector work finishing before capture. Implement reconciliation for missing IDs and explicit handling of duplicates and uncertain identity. Comparing CRM creation time with a reliable source timestamp can be a conservative signal, but does not prove which duplicate person is canonical. Confirm the business rule for new versus existing people before enabling live routing.

Processing performance. Keep database writes out of loops, use selective lookups, and test batches as well as individual Flow interviews. Verified indexes include Submission Key, Lead, Contact, Owner, and Submission Number. Form Key and Processing Status are currently shown as not indexed. Assess query selectivity and indexing needs as volume grows; avoid scanning payload text.

Failure recovery. Implement bounded retries with delay, an exhausted-retry review path, and monitoring for stale Received and Pending CRM Match records. Capture actionable error details. Avoid blind status resets and concurrent manual retries. Source ingestion and downstream processing are separate failure boundaries; monitor both.

Sales access and responsibility. Define who owns submissions versus Tasks, confirm queue membership, and verify Sales access to both submission history and the related person/account. Test the actual integration execution identity and least-privilege permissions. Queue assignment alone is not a notification or SLA process.

Reporting and retention. Track intake counts by form and source time, pending/failed volume, age, routing latency, and outcomes. Follow Up Task ID is text, so cross-object Task reporting needs an explicit report/data design. Add typed attribution fields if needed. Agree retention and archive rules for personal data and full answers; do not log credentials.

Versioning. Version the input contract and configuration when meanings change. Preserve compatibility for existing forms. Maintain Flow metadata and configuration in source control with a repeatable deployment and rollback plan.

Readiness and acceptance criteria

The October 1 handoff recorded successful synthetic capture, sequential replay protection, Lead/Contact routing, and Lead-conversion linkage. It also recorded unfinished External Action registration, integration access, queue membership/notifications, new-versus-existing classification, automatic reconciliation, source packaging, and full form UAT. Those readiness items were not reverified on October 6.

Before connecting real form traffic, verify:

  1. The intended business unit can execute the registered active capture action using the actual integration identity.
  2. Two distinct submissions by the same person preserve two separate answer snapshots; replaying one event preserves one original record.
  3. Missing, malformed, delayed, converted, and ambiguous person identities enter defined outcomes without duplicate Lead creation.
  4. New connector-created Leads and pre-existing people follow the approved business rule.
  5. Sequential and simultaneous retries do not duplicate downstream work; failures remain visible and recoverable.
  6. Sales can see the submission and related person, receive the agreed notification, and work the queue.
  7. Representative peak-volume testing meets the agreed latency and backlog targets.
  8. Flow versions, configuration, access, monitoring, and rollback instructions are deployable and documented.

The recommended implementation remains one reusable capture Flow plus durable submission history and modular processing. Add typed fields and child execution records when the business needs them, while keeping the original event contract stable.

Maintaining and deploying this guide

README.md is the authoritative documentation source. Run python3 scripts/build_guide.py to regenerate the HTML static resource and small Visualforce wrapper. Review the generated page before deploying it. The generator uses only Python standard libraries and handles the Markdown subset used in this README.

Deploy the static resource, documentation page, and custom tab using manifest/documentation.xml; these components do not install or activate the submission Flows. Grant Visualforce page access and tab visibility to the intended internal audience. This guide has no Apex controller and does not query or modify CRM records.

For manual installation, create a Visualforce page named MarketingSubmissionGuide, first upload docs/generated/MarketingSubmissionGuide.html as the private static resource MarketingSubmissionGuideContent, then paste the generated page source and enable Lightning availability. Create a Visualforce tab named Marketing_Submission_Guide with label Marketing Submission Guide. Initially expose it to System Administrator; expand access deliberately for the intended audience.

For future releases, edit this README, update the version and verification dates, rebuild, deploy, and check the live tab, table formatting, section links, and page access. Keep prior generated files to roll back a documentation release. Removing this documentation tab/page does not remove any submission records or automation.
